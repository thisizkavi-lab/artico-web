# CH53 — つながった短い発表をする / Giving a Presentation

**この章でできるようになること:** 目的、つながった要点、終わりが明確な短い発表を行い、その後の質問に対応できます。

<!-- source-heading: Study -->
## 学習

発表では、つなぎ言葉の一覧だけでなく、伝える中身が必要です。聞き手に何を理解してほしいか、何を決めてほしいかを選びます。そのうえで、始まり、互いにつながる少数の要点、終わりの順に組み立てます。聞き手が内容の流れを追えることが大切です。

**Today I'd like to explain...** は、今日説明したい内容を示す始め方です。**The purpose of this presentation is...** は、発表の目的を明示します。**I'll start with the problem, then explain the proposal.** は、まず問題、その後提案を説明するという道筋を知らせます。

**First** は最初の点、**Next** は次の点、**Now let's look at...** はここから見る内容、**Finally** は最後の点へ進む合図です。終わりには、**To sum up...** でまとめたり、**I'd like your feedback before we decide** で決定前の意見を求めたりできます。言葉を置くだけでなく、その後に実際の情報を続けます。

<!-- source-heading: Facts for an original model -->
### 見本で使う事実と提案

見本は、次の架空のチームの状況を使います。

> This fictional team has difficulty finding the approved version of a document. The proposal is to use separate folders named **Drafts** and **Approved**, record a document's owner, and review the trial after one week. It is a proposal for this scene, not a required software method.

チームは、文書の承認済みの版を見つけにくくなっています。案は、**Drafts**「下書き」と **Approved**「承認済み」という別々のフォルダーを使い、各文書の担当者を記録し、一週間後に試行を振り返ることです。この場面の提案であり、必須のソフトウェア利用方法ではありません。

<!-- source-heading: Connected model -->
### 一つにつながった発表の見本

次の英語は、始まりから終わりまでつながった発表です。まず全体を読み、その後の日本語の説明で、段落どうしの関係を確認してください。

“Good morning, everyone. Today I'd like to explain a proposal for organizing our shared documents. I'll start with the problem, then describe a small change we could try.

“At the moment, several versions of a document can have similar names. People sometimes open an older version because it isn't clear which one is approved. That creates extra checking and repeated questions.

“My proposal has two parts. First, we would use separate folders called Drafts and Approved. That would make the status easier to see. Second, we would record who is responsible for each document, so people know whom to ask when something is unclear.

“Now let's look at the trial. We could test the arrangement with one project for a week. At the end of the week, we would ask the team what was easier and what still caused confusion. We haven't measured an improvement yet; the trial would help us find out.

“To sum up, the proposal is to separate draft and approved versions and identify each document's owner. I'd like your feedback before we decide on the trial. What questions or concerns do you have?”

最初の段落では、共有文書を整理する提案を説明するという目的を述べています。先に問題を話し、次に試せる小さな変更を説明すると予告しているので、聞き手は話の道筋が分かります。

二つ目の段落では、現在の問題を説明しています。複数の版が似た名前を持ち、承認済みの版が分からないため、古い版を開くことがあります。その結果、確認の手間と同じ質問が増えます。提案がなぜ必要かを理解するための情報です。

三つ目の段落では、案を二つに分けています。一つ目は下書きと承認済みのフォルダーを分け、状態を見やすくすることです。二つ目は文書の担当者を記録し、不明な点を誰に尋ねるか分かるようにすることです。二つとも、前の段落の問題につながっています。

四つ目の段落では、いきなり全体へ導入せず、一つのプロジェクトで一週間試す案を述べています。週の終わりに、何が楽になり、何がまだ混乱を生んだかを聞きます。改善はまだ測定していないため、成果が出たとは言っていません。試行によって確かめたい内容を示しています。

最後の段落は、二つの提案をまとめ、試行を決める前に意見を求めています。聞き手に求めている返答は、質問や心配な点です。話の目的と、相手にしてほしいことが対応しています。

つなぎ言葉が整理しているのは、実際の情報です。話し手は現在の問題、提案、まだ分からない結果を区別しています。**Could** と **would** は、変更を可能性として提示しています。すでに承認された指示として述べているわけではありません。

<!-- source-heading: Answer an audience question -->
### 聞き手の質問に答える

**Audience member:** Who would move the approved documents?  
**Presenter:** That's something we need to decide. My suggestion is that each document's owner would do it. What do you think?  
**Audience member:** Would the whole team use this immediately?  
**Presenter:** No. The proposal is a one-week trial with one project.  

承認済み文書を移す担当は、まだ決める必要があると答えています。そのうえで各文書の担当者がする案を示し、意見を尋ねます。すぐにチーム全員が使うかという質問には、対象は一つのプロジェクト、一週間の試行だと答えています。未決定の部分と、提案の範囲を分けています。

答えが分からないなら、**I don't have that information yet. I'll need to check.** と言えます。「まだその情報がありません。確認する必要があります」という返答です。

質問が不明確なら、**Are you asking about the trial or the later rollout?** と、試行についてか、その後に使用範囲を広げる導入についてかを確認します。**Rollout** は、変更をより広い範囲へ導入することです。後で対応する意思がある場合には、**I'll check and get back to you tomorrow** と、確認して翌日返答すると伝えられます。実際にするつもりの対応だけを約束します。

<!-- source-heading: Plan your own short version -->
### 自分の短い発表を組み立てる

五つの問いを使って準備します。話題は何ですか。なぜそれが大切ですか。聞き手に必要な二つの要点は何ですか。何がまだ不明ですか。どのような返答を求めますか。要点だけでなく、その関係も考えると、一つにつながった発表になります。

この章の改まった始め方を、全部入れる必要はありません。**To kick things off...** は、会話に近い始め方として使えます。**The purpose of this presentation is...** は、目的を明確にします。すべての文を改まった形にするのではなく、自分がしたい発表に合う言葉を選びます。

<!-- source-heading: Practice -->
## 練習

1. つながった見本を一度声に出して読みます。その後、隠して、上の事実から問題、二つの変更案、試行を説明してください。一人なら、発表後に聞き手の質問を読み、それに答えます。
2. 別の架空の提案を使います。原文の設定は次のとおりです。 **a team wants a shared lunch schedule because break times are unclear; post the planned times; identify who updates them; ask for feedback after a week.** 休憩時刻が不明確なので、共有の昼食予定がほしいチームです。予定時刻を掲示し、更新する担当者を示し、一週間後に意見を求めます。始まり、つながる二つの要点、終わりを組み立ててください。見出しだけでなく、発表全体を声に出します。
3. 聞き手が、与えられた事実には答えがない質問をします。規則を作らず、確認が必要だと伝えてください。

<!-- source-label: Sample short talk: -->
**短い発表の例:** “Today I'd like to explain a proposal for our lunch schedule. At the moment, break times are unclear. First, we could post the planned times in one place. Second, we could name the person responsible for updates. We could try this for a week and ask what still needs work. What concerns do you have?”  

昼食予定の提案という目的、現在の不明な休憩時刻、予定を一か所に掲示する案、更新担当を決める案、試行と振り返り、聞き手への質問がつながっています。

<!-- source-label: Possible unknown-answer response: -->
**答えが分からない場合の例:** “I don't have that information yet. I'll need to check before answering.”  

まだ情報がないと伝え、答える前に確認すると述べています。知らない内容を確定した事実にしていません。

後で、見本を見ずに発表してください。聞き手が目的を言えるか、事実と提案を分けられるか、求めた返答が分かるかを確認します。速さや一字一句の一致より、明確でつながった内容を優先します。
